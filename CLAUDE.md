# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Scam Shield: Stop, Check, Tell" is a game that teaches kids aged 8–12 to spot scams. It's a React + TypeScript + Vite web app that works on tablets and is hosted as static files. `README.md` is the design spec and `PROJECT.md` tracks next steps. Read both before building anything.

## Commands

- Install: `npm install`
- Run: `npm run dev`
- Build (type-checks first): `npm run build`
- Lint: `npm run lint` (oxlint)
- Link server (`worker/`): `npm install` there, then `npm run dev` (port 8787; needs the Safe Browsing key in `worker/.dev.vars`, and `.env.development.local` with `VITE_LINK_SERVER=http://localhost:8787`) or `npm run deploy`; `npm run test-pages` runs the made-up pages in `worker/test/pages.ts` through the AI check (real Claude calls), so rerun it after changing `worker/src/page.ts`; likewise `npm run test-questions` runs the tricky questions in `worker/test/questions.ts` through Buddy's answers (port 8798), so rerun it after changing `worker/src/ask.ts` or `src/chat/askRules.ts`. The keys are secrets (`npx wrangler secret put SAFE_BROWSING_KEY` and `ANTHROPIC_API_KEY`, locally in `worker/.dev.vars`): never put them in a committed file or in the chat, the repo is public. The Worker allows 20 checks a minute per person
- Tests: `npm test` (Vitest). `src/scenarios.test.ts` checks every scenario file; its list of target names per fake screen mirrors the `<Field name=...>` and `useMark` names in `src/mockups/`, so update it when you add or rename one

## Architecture

The game is data-driven. Every scenario uses the same screens, and scenarios differ only in their data in `scenarios/NN-<slug>.json` (loaded in filename order by `src/scenarios.ts`; the format is `Scenario` in `src/types.ts`). Scenarios 4–5 are set aside in `scenarios/later/`, which isn't loaded.

**Menus** (`src/router.ts`): every place in the app has an address after the `#` (`#/`, `#/learn/2`, `#/learn/done`, `#/ask`, `#/check/picture`, `#/check/link`, `#/check/message`, `#/grown-ups`), so the back button works and links can open any part. `App.tsx` picks the screen for the address; add new places to `Route` there. The home screen (`MainMenu`) follows the cream mock-up ("Look and feel" in `PROJECT.md`, but without a tab bar): a header card with the logo, tagline and a gear for grown-ups, then two big warm cards: **Check something** (opens the chat, which leads to the right checker) and **Learn about scams** (the game, which is becoming the tutorial). The cards are `OptionCard` (`screens/`), also used for the chat's answers so they look the same: a coloured icon tile in one of four warm, close tones (orange, peach, gold, amber), a title, an optional short line and an arrow. Menu icons are in `src/icons.tsx` (simple line icons, never emojis). One rounded font everywhere (Nunito); the fake screens keep the real phone font.

**Tools** (`src/tools/`, wireframes: nothing is really checked, sent or saved): every tool screen uses `ToolScreen` (header with Menu on the first step and Back after, a slim "Step 1 of 3" progress bar, one step at a time with a clear heading, and a quiet preview note at the bottom) and ends on `ResultView` (what was checked, the risk level as a coloured heading, numbered clues, "show a grown-up", then Check something else / I'm done). `PictureCheck` is Choose → Check → Result (the result is still the example). Pictures really come in through `tools/picturePicker.ts`, the one place to change for the phone app: `pickPicture` (the browser's picker: photo library, or the camera on touch devices; in the app, swap in the phone's picker, e.g. Capacitor Camera) and `receivePicture`/`takeReceivedPicture` (pictures pasted or dropped anywhere on the page now, and in the app the share button). `preparePicture` shrinks it to 1568px on its longest side and saves it again as a JPEG, which drops hidden details like location; `TextCheck` does links and messages (Paste → Result, clues marked in the text with `MarkedText`). **Links are really checked**, on the device, by `tools/linkCheck.ts`: facts about the address only, never visiting it. The address is taken apart with the Public Suffix List (`tldts`, so www.bbc.co.uk is bbc.co.uk and my-page.vercel.app is its own website), and a link can be typed without https:// or pasted inside a message (every link in it is checked; the riskiest is shown). Clues: pretending to be a brand from `tools/brands.ts` (the verified official domains; missing, added, changed or swapped letters, lookalike numbers, letters from other alphabets via `tools/lookalikes.ts`, a real brand address used as a subdomain like roblox.com.evil.net), with fan websites of games and shows (`fans: true`) only a smaller clue unless there are logging-in or prize words; a real brand address in the path; an @ hiding the real address, numbers instead of a name, free website makers, known betting websites (`GAMBLING_SITES`, including prediction markets like Kalshi) and adult websites (`ADULT_SITES`, and endings like .xxx), both only "Be careful", short links, very long addresses, risky endings, bait words, http. Each rule has tests in `linkCheck.test.ts`; add a test for every new rule or brand. Then, while "Checking" shows, `tools/linkLookup.ts` asks our server (`worker/`, a Cloudflare Worker that holds the Google key) for facts the device can't get: Google Safe Browsing, how new the website is (RDAP), whether it exists (DNS), and where a short link really goes (it only follows short links and keeps nothing). Only when none of that finds anything, and it isn't a real brand's website, the Worker reads the page (`worker/src/page.ts`: text and forms only, no scripts) and asks Claude Haiku 5.5 fixed yes/no questions (copies a brand, asks for a password or card, free prizes, unreal deals, downloads, free paid sports and shows (unlicensed streams), tricky pop-up ads, rushing you, betting, not for kids; the page's code is checked for known pop-up ad networks too); the page is treated as untrusted data, and the AI can add clues but never say a website is fine. A website that turns the Worker away (bot protection: 401, 403, 429 or 503) gets `pageBlocked`, a "Be careful" clue, since nobody could check it; known betting and adult websites aren't read at all. The Worker also asks Cloudflare's family DNS filter about every website (`isAdult`: blocked by the family filter but not the security-only one means adult), so adult websites missing from the list are still "Not for kids". `withFacts` turns all of this into kid-words clues, with fixed wording (the AI never writes what kids read), and lists good signs when there are no clues (tests in `linkLookup.test.ts`). With no server (`VITE_LINK_SERVER` unset) or no answer within 8 seconds, the device's clues show on their own. A link typed in the chat fills in the link checker. Every check returns a `CheckResult` (`examples.ts`: a risk level, never "safe", and clues with a label, a kid-words reason and the words to highlight); the AI will fill these in, and for now they're made-up examples. `GrownUpsScreen` is a parent gate, then the settings (written for adults).

**Parent setup** (`src/setup.ts`): nothing a kid checks or asks is sent anywhere until a grown-up ticks "I agree" in `GrownUpsScreen`, which lists what is sent where (saved in `localStorage` with `storedSwitch`; unticking stops everything straight away). Until then the game works as usual, the link checker only checks on the device (`lookUpLink` returns null, and a quiet note says so), Buddy doesn't answer questions or listen, and the picture and message checkers show `SetupFirst` ("Ask a grown-up first"), whose button opens `#/grown-ups/<tool>` and comes back to the tool afterwards. Every new feature that sends something must check `isSetUp()`/`useSetUp()`. The challenge build starts set up, with Buddy's answers on, via `VITE_SET_UP_BY_DEFAULT=true` in `.env.production` (false for now); a grown-up can still turn things off.

**Ask Shield Buddy** (`src/chat/`): a chat where Buddy helps a kid check something that feels weird. Buddy's messages show moving "typing" dots, then appear whole (`useDots`; `REVEAL` in `ChatScreen` switches back to the game's typewriter), with the same reading pauses, tap-anywhere to hurry, and mood pictures and moves as the game; then answers slide up to tap. The conversation carries on after leaving to check something (`chat/session.ts`, in memory only, gone on reload): Buddy greets once, then on coming back reacts to what the check found (`BACK_AFTER` in `script.ts`, from `noteCheck` in `ResultView`) or, with no check in between, picks up where it was. Everything Buddy says, and every answer, is in `chat/script.ts` as steps (`STEPS`): each has Buddy's lines, a mood and the answers, and an answer leads to another step or leaves the chat (to a tool). Picture, link and message each get one short line and one button that opens their checker. "I'm not sure" tells the kid it's fine to stop, and to ask a grown-up or ask Buddy in the box below (typing or talking); the box glows to show where (`pointAtBox`). The player can also type a question in the box: it shows as their message. Questions are handled strictly, in layers (`src/chat/askRules.ts`, shared by the app and the Worker, with tests in `askRules.test.ts`; add one for every new rule): anything with a real website name (via the link checker, so `.site` and `.gift` count) gets the link checker; personal details (email, phone, address, password, login code, name, school) or something upsetting (hurting themselves, private photos, touching, bullying, threats) get scripted lines (`personal`, `upset` in `script.ts`) and are never sent, then or later. Anything else, when setup is finished and "Let Shield Buddy answer your child's questions" is on (both saved in `localStorage`; see **Parent setup**) and there's a server, goes with the last few messages to the Worker's `/ask` (`chat/askBuddy.ts` → `worker/src/ask.ts`), where Claude Opus 5.5 first labels the question (`safety`, `offTopic`, `personal`, `upset`) and only writes 1–3 short bubbles for `safety` ones; the others get scripted lines (`TOPIC_STEPS`). The system prompt keeps it simple and calm, never says something is safe or real, says sure-fire tricks are scams in absolute words (free Robux, V-Bucks or Minecoins are always a scam and only come from the game itself; anyone asking for a password or code for a prize is always a scammer; a prize paid with a gift card is always a scam), and treats the kid's messages (which may hold pasted scam text) as untrusted. Its words are then checked in code (`answerProblem`: at most 3 bubbles of 160 characters, no links, emails, phone numbers, emojis, personal details, "safe" except "stay safe" or "keep you safe", "it's real/legit", "don't worry", or scary words; and a question about free game money must get a bubble naming it with "always", "never", "only", "no such thing" or "doesn't exist") and thrown away if any rule is broken. Buddy's typing dots show while it waits; then a scripted step from `ANSWERED` in `script.ts` always adds a line pointing to a grown-up and the checker button. If it can't answer (off, no server, error, refusal), Buddy's scripted replies are used (`replyTo`: `typed`, or `askFailed`). Nothing typed is kept, here or on the server. The microphone lets the player ask out loud (`src/voiceInput.ts`, the browser's Web Speech API: free, but Chrome and Safari send the voice to Google or Apple to turn it into text): tap to start and stop, the words fill the box as they're heard to check before sending, and it's off until setup is finished and a grown-up turns it on (saved in `localStorage`); browsers without speech recognition don't show it. `script.test.ts` checks every step can be reached and none is a dead end. Its classes start with `ask-`, because the Discord-style fake screen already uses `chat-`.

**Game flow** (`src/screens/`):
1. Learn about scams plays the scenarios in order (the dev console can jump to any one). Each next scenario replaces the last in the browser history, so back leads to the menu.
2. `ScenarioScreen`: the scam plays in on a fake screen; Shield Buddy says `buddy.intro`, `buddy.explain` and `buddy.choices`; then the Do it / Check with Scam Shield / Tell an adult buttons slide up.
3. `DoItScreen` (only after Do it, only if the scenario has `doIt`): where the scam leads, e.g. a fake website.
   `CheckItScreen` (after Check): a practice version of the matching tool with the scam filled in (`checkIt`: `message`, `link` or `picture`), then its result (`tools/tutorial.ts`), with "See what happens" instead of the tool's own buttons (the chat isn't told about it). Links are really checked; messages and pictures find the scenario's "Spot the clues" items.
4. `OutcomeScreen`: Buddy explains the result, then "What if you had…" cards (worded by `whatIf`) show the other two choices. Results are always `do` → red, `check` and `tell` → green.
   Then `SpotScreen`: the scam comes back and the player taps the clues on a short checklist.
5. `RecapScreen`: Stop, Check, Tell with a 3-step progress bar. Each step highlights a red flag on the fake screen while Buddy explains it. Tell ends with `recap.tip` (what you can do, e.g. a family code word), then `SummaryCard` (`recap.summary`: what you can do, and "Make sure to avoid").
6. `EndScreen`: after "Finish" on the last scenario, with the player's badges.

**Badges** (`src/badges.ts`): earned during play (all clues found, telling an adult, finishing) and saved in `localStorage`. `BadgeToast` (`screens/Badges.tsx`) shows "New badge!" when one is earned; `BadgeList` shows them all on the end screen.

**Fake screens** (`src/mockups/`): `Mockup` picks the component for a scenario's `mockup` type. Devices are `PhoneFrame` (iPhone; `dark` for full-screen apps, optional message box) and `TabletFrame` (iPad held sideways, scales to fit with container query units); `SafariBar` is the iPad Safari toolbar. Nothing on a fake screen is a real link, button or form field. Images (logos, photos) live in `public/images/` and are named by path in the scenario files.

**Recap targets:** recap items are `{ target, highlight?, text, screen? }`. `target` names a content field, `highlight` is an exact piece of text inside it, and `screen: "doIt"` points at the Do it screen instead. Mock-ups render text through `<Field name=...>` (`Field.tsx`), and non-text parts (a video, a box of comments) use `useMark` (`marks.ts`); both highlight and scroll into view. A list of texts is targeted as `message1`, `message2`, and so on. A recap item with a `spot` name (e.g. "Someone rushing you") is also on the "Spot the clues" checklist (`SpotScreen`); `spotAlso` lists other places on the screen that count as finding it (e.g. the video as well as the caption for "A free prize"), and `spotHint` is what Buddy says when the player taps Hint.

**Look and feel** (cream; see "Look and feel" in `PROJECT.md`): colours are CSS variables on `:root` in `src/index.css`: `--bg` (warm cream, with soft corner glows), `--surface` cards, `--ink` brown text, `--muted`, `--hairline`, `--accent`/`--accent-2` (the orange of main buttons, the player's chat bubbles and progress; `--accent-gradient` combines them), `--on-accent`, and `--sun`/`--teal` for touches. Check results use soft `--danger-*` (rose), `--unsure-*` (honey) and `--good-*` (sage) colours (`-bg`, `-line`, `-ink`), always with an icon (`DangerIcon`, `UnsureIcon`, `GoodIcon`) so colour isn't the only sign. Icon tiles use the warm `tone-*` classes (orange, peach, gold, amber). Use the variables rather than new hard-coded colours, except on fake screens. Fonts: `--font-body` and `--font-display` (headings and buttons), both Nunito for now, loaded from Google Fonts in `index.html`; `.mockup` resets to the real phone font. Keep screens calm: big rounded cards, few words, one main button.

**Shield Buddy** (`src/buddy/`): a yellow shield with a face and hands; one image per mood from `shield_buddy/` (`happy`, `curious`, `thinking`, `worried`, `cheering`, `neutral`), with typed-out speech bubbles (`useTypewriter`: a slow, kid-friendly pace with pauses after punctuation, then a reading pause before the next bubble; tapping anywhere on the screen except a button finishes the typing or skips the pause). Every bubble stays: messages added later type out under the earlier ones, and the stack fades out at the top and scrolls (no scroll bar). Buddy does a move per mood with each new message (CSS in `index.css`). The artwork is 1000×1000 with the character centred side to side and sitting at the bottom of the image, the same for every mood, so Buddy lines up with the bottom of its newest bubble; keep new artwork laid out the same way. **Read-aloud** (`src/readAloud.ts`, switch in `screens/ReadAloudToggle.tsx`, off by default, saved in `localStorage`): Buddy's own voice reads each of Buddy's lines: the Worker's `POST /speak` (`worker/src/speak.ts`) makes it with Google Cloud Text-to-Speech (Chirp 3: HD voice `en-US-Chirp3-HD-Alnilam`, key `GOOGLE_TTS_KEY`), keeps each line's audio in KV (`SPEECH`) so it's only made once, and counts the month's characters, stopping new lines at 500,000 (half of Google's free amount; see `GET /usage`). Only Buddy's own lines are ever spoken, never what a kid types. If the server doesn't answer within 5 seconds or the month is used up, the device's own voice (Web Speech API) reads it; with it on, each bubble appears whole and the next waits until the voice has finished (a tap stops the voice and moves on). Keep Buddy's lines in the scenario data, not in markup.

Animations respect `prefers-reduced-motion` (`src/motion.ts`).

**Dev console** (`src/dev/`, dev server only): fast mode, jumps to any screen, and pickers for colour palettes (`dev/palettes.css`) and fonts (`dev/fonts.css`), for testing. It must be removed before shipping; the steps are in `PROJECT.md`, and every touchpoint is marked `DEV CONSOLE`. Keep that list up to date if you add to it.

## Content rules (these apply to all scenario text and UI copy)

- Write at about an 8-year-old reading level, with simple words. Keep one idea per screen, with big buttons and large text. The text on the fake screens can be realistic; everything Buddy and the game say must be simple.
- Scenarios 1–3 show real apps and brands (iPhone, Safari, Google, Roblox, YouTube) so they match what kids actually see; scenarios 4–5 (set aside for now) use made-up names (PixelPals, ShopZoom). Never include working links. Whether to keep real brands is still being decided (see `PROJECT.md`).
- Consequences should feel realistic but not frightening or graphic.
- No shame. Wrong choices get "Here's what to watch for next time," never "You failed."
- No emojis in the game's own interface (buttons, labels, headings). Emojis are fine inside the fake scam screens.
- Shield Buddy never hints before the choice: its intro, explanation and list of choices stay neutral. It isn't a trusted adult: its lines always send kids to a real grown-up. All its lines are scripted, never generated, except its answers to questions kids type in the chat, which the AI writes (`worker/src/ask.ts`) and which are always followed by a scripted line pointing to a grown-up.
- Keep the key lesson: don't do what the scam asks. Check it with Scam Shield, and show a grown-up. Check and Tell both stop the scam, and the Check outcome always ends with showing a grown-up.
- Every scenario ends with what the kid can do next time (`tip` and `summary`), worded gently.
